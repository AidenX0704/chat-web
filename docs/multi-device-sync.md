# 多端同步设计

会话数据在服务端 SQLite 里，同一账号在手机、平板、电脑上看到同一份历史。
本文说明数据怎么存、怎么传、两台设备同时改怎么不互相覆盖，以及边界在哪。

## 1. 存储分层

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 账号、登录态、审计 | SQLite 用户/会话/审计表 | 见 [server/README.md](../server/README.md) |
| 会话元数据 | «chats»（标题、时间、版本、消息数、根消息） | 侧边栏只查这一张表，带 «(user_id, updated_at)» 索引 |
| **单条消息** | «chat_messages» 一行一条，含 «revision» 与 «position» | 消息 JSON 与前端 «Message» 类型一一对应，服务端不理解内部结构 |
| 删除墓碑 | «chat_message_deletions» | 增量拉取时要告诉客户端「这条被删了」，保留 7 天 |
| 附件原件 | «DATA_DIR/<用户>/<文件 id>» | 另一台设备要能显示同一张图，原件必须留在服务端 |
| 会话 ↔ 附件引用 | «chat_files» | 删除会话时据此判断原件是否还有别处引用 |
| 历史导入的解析暂存 | 浏览器 IndexedDB | 只是解析缓冲，导入成功后一次性推给服务端 |

消息按行存的直接好处：**流式生成时每次保存只写正在生成的那一条消息**（约 2KB），
而不是把整份会话（几十 KB 到上百 KB）反复上传。

## 2. 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | «/api/chats» | **只要标题列表**（id、title、createdAt、updatedAt、version、messageCount） |
| GET | «/api/chats/:id» | 打开会话时拉全量消息 |
| GET | «/api/chats/:id/messages?since=N» | **增量**：只返回版本 N 之后变化的消息与被删的 id |
| GET | «/api/chats/:id/events?since=N» | **实时推送（SSE 长连接）**：建连时立即补发 N 之后的差量，之后另一台设备每次写入 / 重命名 / 删除即时推送 |
| PUT | «/api/chats/:id» | 保存变更（«baseVersion» 乐观锁 + 只提交变化的消息） |
| PATCH | «/api/chats/:id» | 只改标题 |
| DELETE | «/api/chats/:id» | 删除，并清理没人再引用的原件 |
| POST | «/api/chats/import» | 历史导入：事务内整库替换 |
| PUT/GET/DELETE | «/api/files/:id» | 附件原件上传 / 下载 / 删除 |

保存请求的形状：

```json
{
  "baseVersion": 12,
  "title": "会话标题",
  "createdAt": 1700000000000,
  "updatedAt": 1700000009000,
  "rootMessageId": "m-1",
  "upsert": [{ "position": 7, "message": { "id": "m-8", "role": "assistant", "...": "..." } }],
  "deleted": ["m-5"],
  "fileIds": ["file-a"]
}
```

## 3. 打开应用的加载顺序

1. 登录成功 → «GET /api/chats»：**只有标题**，侧边栏立刻出来；
2. 点开某个会话 → «GET /api/chats/:id»：才拉正文；
3. 切回页面 / 每 20 秒 → 拉一次列表（元数据），发现某会话 «updatedAt» 变了，
   再调 «GET /api/chats/:id/messages?since=本地版本» **只取变化的那几条**。

实测一次「打开应用」的正文流量：0 字节；打开一个会话：1.45ms（60 条消息）。

## 4. 写：只提交有变化的消息

客户端为每个会话维护一份「已同步指纹」（消息 id → 位置 + 内容指纹）：

- 保存时逐条比对，只有新增或内容变化的消息进 «upsert»；
- 上一次有、这次没有的 id 进 «deleted»；
- 服务端在一个事务里递增会话版本、更新对应行、记录删除墓碑。

浏览器实测（两轮对话、4 次保存）：**单次请求体 0.5～1.1KB，最多 3 条消息**；
同样场景如果传整份会话会到几十 KB，且随会话变长线性增长。

## 5. 两台设备同时改

每个会话有一个自增 «version»，写入用 «UPDATE ... WHERE version = ?» 完成「校验 + 写入 + 自增」，没有竞态窗口。

```text
PUT /api/chats/:id  { baseVersion: 7, upsert: [...] }
  → 200 { version: 8 }
  → 409 { error: { code: "version_conflict" }, current: { version: 9 } }
```

收到 409 时客户端不报错，而是：整份重拉当前会话 → 按消息 id 求并集合并 →
重新算一次差量 → 带新版本重试（最多 3 次）。合并规则：

- 消息 id 是客户端生成的 UUID，两台设备不会撞车，并集即可；
- 同一条消息内容不同时**先比内容长度**（另一台设备可能正在流式生成，不能把它截断成「已停止」），
  一样长才看状态（done 优于 streaming）；
- 标题取 «updatedAt» 更晚的一方。

版本号「客户端比服务端还新」（例如刚导入覆盖过）时，增量接口返回 409 «version_ahead»，客户端整份重拉。

## 6. 保存节流与实时推送

流式生成时 store 会在动画帧触发保存，客户端在 «remoteDb.ts» 里做了两层合并：

- 同一会话的并发保存合并成「最后一次快照」；
- 流式生成期间两次写入之间至少间隔 400ms，生成结束（done / stopped / error）时立刻落盘；
- 服务端写入成功后通过内存事件总线通知同账号下其他正在订阅 «GET /api/chats/:id/events» 的设备，
  按各自上次已推送版本号查出差量帧（«event: delta»）即时下发，并通过 «x-client-id» 抑制发起标签页自身回声。

所以另一台设备打开同一个会话时，可以看到回复**边生成边实时同步**；一次长回复大约 2 次/秒的服务端写，每次只写一条消息行（实测单连接 11582 次/秒，p99 0.22ms）。

## 7. 多端行为对照

| 操作 | 另一台设备何时看到 |
| --- | --- |
| 正在查看的会话流式回复 | 实时推送（约 400ms 一次增量帧，生成结束立刻收尾） |
| 正在查看的会话重命名 / 删除 | 立即（SSE 推送 «delta» / «deleted»，删除时自动回到新对话） |
| 其他设备新建会话 | 切回页面立即，否则最多 20 秒（侧边栏轻量元数据刷新） |
| 踢设备 | 被踢设备的令牌立刻失效，活跃 SSE 连接立即断开，下次请求 401 → 回登录页 |

## 8. 已知边界

- **单进程实时推送**：事件总线在进程内存中，适合单 Node 进程部署（SQLite 亦推荐单进程）。
- **后端模式没有离线能力**：断网读不到历史（纯静态模式仍完全离线，走 IndexedDB）；断线后 SSE 会指数退避重连，带上上次版本号通过 «since» 自动补发漏掉的消息。
- **删除墓碑保留 7 天**：客户端每次打开都会重新拉列表与正文，不需要更长。
- **合并偏向「不丢消息」**：同一消息双方都改过时，内容更长的一方胜出，不做逐字 diff。
- **导入时附件后置上传**：会话在事务里替换，附件随后逐个上传；失败会「会话在、图片缺」，重导即可修复。
