# SQLite 撑得住「一个人多台设备 + 十几个人同时在线」吗

**结论：能，而且余量有两个数量级以上。** 现在会话正文也存在服务端 SQLite 里了，
下面用实测数据说明上限、把真实负载折算成每秒请求，再给出会踩坑的场景和切 PostgreSQL 的判据。

所有数字来自本机实测（macOS + SSD，Node 22，better-sqlite3 13 / SQLite 3.54），复现命令：

```sh
cd server && pnpm bench
```

---

## 1. 先算需求：这个平台到底有多大压力

服务端 SQLite 存三类东西：**账号与登录态**、**会话正文（JSON）**、**附件元数据**（附件本体在数据目录）。

| 场景 | 频率 | 读写类型 |
| --- | --- | --- |
| 打开页面校验登录态（`GET /api/auth/me»） | 每次访问 1 次 | 主键索引读 |
| 登录 | 每人每天几次 | 一次 scrypt + 一次插入 |
| 登录态续期 | 每个会话每分钟最多 1 次写 | 单行更新 |
| **拉会话标题列表**（登录、切回页面、每 20 秒） | 60 台设备 ÷ 20 秒 ≈ **3 次/秒** | 索引扫描，只读元数据 |
| **保存消息**（流式回复期间） | 每会话 1.3 次/秒（客户端合并到 750ms 一次） | 事务内更新一行消息 + 会话版本，单条约 2KB |
| 打开某个会话 | 用户点击时 | 索引读 60 条消息，约 1.45ms |
| 增量同步（另一台设备有新内容） | 每会话每分钟最多 3 次 | 索引读 `revision > since` 的行 |

按「20 个用户 × 每人 3 台设备 = 60 个在线设备、其中 3~5 个正在生成回复」估算：

- 消息保存：3~5 × 1.3 ≈ **5~7 次/秒**，每次一行约 2KB
- 列表查询：**约 3 次/秒**
- 打开会话正文：**约 1 次/秒**
- 登录态续期 + 零散写入：**< 5 次/秒**

峰值写入需求大约 **10 次/秒**，每次写一小行。记住这个数字。

## 2. 实测

### 2.1 登录态这类小事务（`auth_sessions» 表）

```text
[1] 单连接串行写入（本服务单实例的真实形态）
  synchronous=NORMAL           并发= 1  写入=5000  吞吐=37875 次/秒  p50=0.02ms  p99=0.04ms  busy=0
  synchronous=FULL             并发= 1  写入=2000  吞吐= 9928 次/秒  p50=0.10ms  p99=0.35ms  busy=0

[2] 多连接并发写（模拟多进程 / 多实例）
  4  个连接  吞吐=25952 次/秒  p99=0.09ms   busy=0
  12 个连接  吞吐=13302 次/秒  p99=2.17ms   busy=0
  24 个连接  吞吐=21427 次/秒  p99=3.99ms   busy=0

[3] 读写分离：12 个读连接 + 1 个写连接（WAL 下读不阻塞）
  写连接     吞吐=13940 次/秒
  12 个读连接合计 18000 次读取，吞吐=205559 次/秒，p99=0.47ms
```

### 2.2 会话与消息（消息按行存，单条约 2KB，每个会话 60 条）

```text
[4] 会话正文（消息按行存，单条约 2KB，每个会话 60 条）
  单连接保存一条消息（事务：更新消息行 + 会话版本）
                               写入=2000  吞吐=11582 次/秒  p50=0.07ms  p99=0.22ms  busy=0
  并发保存同一会话  4 个连接    写入= 800  吞吐=11323 次/秒  p50=0.07ms  p99=3.33ms  busy=0
  并发保存同一会话 12 个连接    写入= 804  吞吐=11214 次/秒  p50=0.08ms  p99=4.39ms  busy=0
  会话列表（10 条元数据）: 0.46ms；整份会话读取（60 条消息）: 1.45ms

口令散列（scrypt N=32768,r=8,p=1）
  单次计算 90～220ms（随机器负载浮动），4 路并发吞吐 26～47 次/秒
```

对照需求：

| 指标 | 需求 | 实测能力 | 余量 |
| --- | --- | --- | --- |
| 消息保存 | ~7 次/秒（每次一行 2KB） | **11582 次/秒**（单连接，p99 0.22ms） | ~1600 倍 |
| 会话列表查询 | ~3 次/秒 | 0.46ms/次，约 2000 次/秒 | ~600 倍 |
| 整份会话读取 | ~1 次/秒 | 1.45ms（60 条消息） | 三个数量级 |
| 登录态写入 | ~5 次/秒 | 37875 次/秒 | 四个数量级 |
| 并发登录 | 十几个人同时登录 | 26～47 次/秒 | 瞬间完成 |

**瓶颈不在这里。** 真实链路的耗时几乎全部来自 DeepSeek 上游的生成延迟（几百毫秒到几十秒），
一次消息写入是 0.07ms——差了四个数量级。

## 3. 为什么扛得住：单写者 + WAL + 短事务

SQLite 的并发模型是「**多读单写**」：同一时刻只有一个写事务，写提交后读者立即可见，
且**读者永远不会被写者阻塞**（WAL 下读的是自己的快照）。聊天应用正好是这个形状：
绝大多数请求是读（拉列表、拉正文、校验登录态），写又短又零散。

本服务为此做的具体设置（见 `server/src/db/index.ts»）：

| 设置 | 作用 |
| --- | --- |
| `journal_mode=WAL» | 读写互不阻塞；崩溃恢复更快 |
| `synchronous=NORMAL» | 只为 checkpoint 做 fsync，写入吞吐约为 `FULL» 的 3.8 倍（37875 vs 9928） |
| `busy_timeout=5000» | 多进程时自动排队重试而不是立刻抛 `SQLITE_BUSY»（实测 0 次 busy） |
| 短事务 | 每个请求一个事务，绝不把网络 IO 放进事务里 |
| 列表只查元数据列 | 侧边栏查询 0.46ms，与消息条数无关 |
| 消息按行存 | 流式生成时一次只写正在生成的那一条，不碰整个会话 |
| 客户端写入节流 | 同一会话合并 + 750ms 最小间隔，把流式生成的写入压到 1~2 次/秒 |
| 登录态续期节流 | 每 60 秒最多写一次 |
| 单进程部署 | 单写者天然无锁竞争，十余人规模最省心 |

## 4. 「一个人多台设备」的额外含义

多设备是**并发读 + 偶尔写**，而且是**写不同行**（不同会话、不同登录态），不会互相争抢：

- 3 台设备各持一个登录态，续期写命中不同行；
- 各自在不同会话里发消息 → 写不同行，完全并行；
- 同一会话两端同时发消息 → 乐观锁 + 消息合并（见 [多端同步设计](multi-device-sync.md)），
  实测「12 个连接写同一个会话」这种最坏情况仍是 11214 次/秒、p99 4.4ms，而真实场景里同一会话不会有 12 个写者。

## 5. 什么时候该换 PostgreSQL

| 信号 | 阈值 | 说明 |
| --- | --- | --- |
| 消息写入 QPS | 持续 > 1000 次/秒 | 单写者开始顶到上限（实测单连接 11582 次/秒的短事务） |
| 在线人数 | 数百人以上且同时生成 | 写入与轮询同时增长，超过单机 IO 更值得横向扩展 |
| 需要多机部署 | 2 台以上应用实例且写入占比高 | 多进程共用文件会吃 `busy_timeout» 排队 |
| 单库体积 | 数十 GB，或单表数千万行 | 备份、VACUUM、checkpoint 时间变长 |
| 需要行级并发更新 / 主从 / 异地多活 | — | SQLite 是单机文件 |
| 附件要进库 | — | 附件已按文件落盘，不要塞 BLOB 进库 |

迁移成本低：数据访问全部收在 `server/src/db/» 的仓储层（`users» / `authSessions» / `throttle» /
`authEvents» / `chats» / `userFiles»），换 `pg» 驱动只需重写这几个文件，路由和业务逻辑不用动。

## 6. 运维要点

- **备份**：`sqlite3 data.sqlite ".backup snapshot.sqlite"»（在线备份，不阻塞写），
  或直接拷贝 `.sqlite» + `-wal» + `-shm»；附件目录 `DATA_DIR» 一并备份。
- **磁盘**：SSD；不要放网络盘（NFS 锁语义不可靠）。
- **监控**：库文件大小、`SQLITE_BUSY» 次数、慢查询、附件目录占用（有单账号配额，见 `FILES_QUOTA_MB»）。
- **清理**：过期登录态、登录失败计数、90 天前的审计日志自动清理；
  上传后一天仍没有会话引用的孤儿附件也会自动删。
- **部署形态**：**一个 Node 进程**。要多进程时 WAL + `busy_timeout» 能跑，但写会排队，收益远小于单进程。
- **清理**：删除墓碑保留 7 天；过期登录态、失败计数、90 天前的审计日志、无人引用的孤儿附件都会自动清理。
- **不要做的事**：把附件二进制存进 SQLite；在事务里 await 网络请求；用 SQLite 当消息队列。

## 7. 一句话总结

十余人、每人几台设备的量级，需求大约 10 次/秒写入和几次/秒的列表查询；
实测单连接就能保存 11582 次/秒的消息（p99 0.22ms）、3.8 万次/秒的登录态小事务，
列表 0.46ms、整份会话 1.45ms。
**这个规模用 SQLite 是合适的选择，不是将就**——等消息写入常态化破千次/秒、或者需要多机水平扩展时，
再按上面的清单迁移到 PostgreSQL。
